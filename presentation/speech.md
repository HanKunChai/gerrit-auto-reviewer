# GERA 自动代码评审系统 — 演讲稿

> 对应 PPT 共 10 页，预计演讲时长 15-20 分钟

---

## 第 1 页：封面

> 【开场，约 30 秒】

大家好，我今天分享的主题是"当 Workflow 遇见 Agent"——讲的是我在做一个自动代码评审系统 GERA 过程中的一些设计思考和优化经验。

这个系统是给我们的 Gerrit 代码评审平台做的，它能自动拉取待评审的变更，用 AI 帮忙看代码，然后把评审意见直接发回 Gerrit。但今天我不打算细讲系统功能，而是想聊聊**设计思路**——AI 到底应该在自动化流程里扮演什么角色。

---

## 第 2 页：问题与动机

> 【约 1 分钟】

先说说为什么要做这个。我们做嵌入式 C 开发，代码评审是一个很重的环节。但人工评审有几个老问题：

第一是**耗时**，变更经常堆积，评审响应慢；第二是**遗漏**，人看多了会疲劳，深层的 bug 容易被忽略；第三是**标准不一致**，不同评审者关注的点不一样。

所以当时我就想：能不能让 AI 自动帮我看代码？但紧接着就来了一个更关键的问题——AI 应该在流程里扮演什么角色？是全交给 AI？全不用 AI？还是各取所长？

---

## 第 3 页：核心设计思想 — Workflow + Agent

> 【约 2 分钟，这是核心页，重点讲】

我的答案是：**能确定的就确定，需要判断的才用 AI**。

大家看这张架构图。上面标了"确定性 Workflow"和"AI Agent"两个区域。一个变更的评审生命周期大概有 13 步，其中 12 步是纯确定性代码——轮询 Gerrit、过滤去重、git fetch、创建 worktree、SVN 合规检查、格式化结果、发回 Gerrit。这些事情用 Python 代码写就行，快、准、零成本。

**只有一步是 AI 做的**——就是让 Claude 读代码、理解语义、发现问题。这一步需要"判断"，是 AI 真正有价值的地方。

最终的比例大概是 90% 确定性代码，10% AI Agent。这个比例不是刻意设计的，而是在迭代过程中自然形成的——**凡是我能用确定性代码解决的，我就不碰 AI**。

---

## 第 4 页：哪些不需要 Agent？

> 【约 1.5 分钟】

具体展开说说哪些环节不需要 AI。

**轮询调度和过滤去重**——就是一个 while 循环加三层幂等检查：跳过自己的提交、跳过正在处理的、跳过已经评审过的。这是最基础的编程逻辑，让 AI 来做纯属浪费钱。

**Git 操作**——shallow clone、按需 fetch、命名 ref、worktree 隔离。这些都是工程问题，我在过程中还踩了 FETCH_HEAD 竞态的坑，后面会讲。但不管怎么踩，这些都是用确定性代码解决的。

**Gerrit API 交互**——标准的 HTTP 客户端，GET 变更、POST 评审，没什么好说的。

**SVN 合规检查**——这个比较有意思。我们公司要求提交代码时附带设计文档、自测报告、需求归档。系统会去 SVN 上检查这些文档是否存在，甚至会下载 Excel 文件读取特定列来验证。这些都是纯数据校验，不需要 AI。

---

## 第 5 页：Agent 用在哪里？

> 【约 1.5 分钟】

那 AI 到底用在哪里？**唯一的 AI 环节：理解代码语义，发现深层问题**。

这里有一个关键决策：我用的是 Claude Code CLI，而不是直接调 Anthropic API。为什么？因为 Claude Code 有两个 API 做不到的能力：第一，它能直接 cat 源文件，自主浏览代码库；第二，它能原生加载 CLAUDE.md 里引用的 Skill 文件。如果用 API，你得把所有文件内容塞进 prompt，成本和效果都不好。

系统跑了 6 个评审维度并行：问题解决评估、安全、内存管理、编码规范、逻辑正确性、业务逻辑。每个维度是一个独立的 Claude 子进程，有自己的专属 Skill。这样做的好处是：每个维度注意力集中，互不干扰；一个维度超时不影响其他维度。

---

## 第 6 页：成本优化 — Prompt 瘦身之路

> 【约 2 分钟，这是优化重点】

接下来讲优化。第一个也是最大的优化：**Prompt 瘦身**。

这个系统迭代了 6 个版本，prompt 的变化是最戏剧性的。

v1 的时候，我把 diff 全文直接嵌进 prompt。问题很明显——上下文爆炸，内网模型处理很慢。

v4 改进了一步：diff 写到文件里，让 Claude 自己 cat 读取。但 13 个 Skill 的评审规则仍然嵌在 prompt 里，每个维度的 prompt 大约 30KB。

v5 做了一个架构级的改动：Skill 文件夹化。把评审规则从 prompt 里拿出来，放到 `.claude/skills/` 目录下，每个维度一个文件夹。然后在 worktree 根目录生成一个 CLAUDE.md，用 `@` 语法引用这些 Skill 文件。Claude Code 启动时会自动发现并加载它们。

结果是：prompt 从 30KB 降到了 400 字节。**99% 的缩减**。而且效果反而更好了——因为 Claude Code 原生加载 Skill 的方式比嵌入 prompt 更自然，上下文空间释放出来给了真正的代码审查。

---

## 第 7 页：成本优化 — 组合拳

> 【约 1.5 分钟】

除了 prompt 瘦身，还有一套组合拳。

**规则引擎前置过滤**——我写了一个正则规则引擎，17 条内置规则，能抓 strcpy、sprintf、Allman 大括号违反这些明显问题。规则引擎跑在 AI 之前，不消耗 token，AI 只需要关注规则引擎抓不到的深层问题。

**结构化 JSON 输出**——强制 Claude 输出 JSON，不输出废话。配合一个 `_strip_thinking()` 函数过滤掉分析性的文本，只保留结论。

**评审结果缓存**——用 change_id 加 revision 做 key，TTL 24 小时。同一个 patchset 不重复评审。

**幂等过滤**——REVIEW_TAG 加 revision 号双重检查，加上 `_in_flight` 集合防止并发重复提交。

**多维度降级**——部分维度失败不丢弃已有结果，标注"未完成"就行；全部失败才跳过提交，等下轮重试。

## 第 8 页：性能优化 — 三层并发

> 【约 1.5 分钟】

性能方面，核心是一个三层并发模型。

第一层是 Review 任务级，用 ThreadPoolExecutor(2)，同时处理 2 个变更。第二层是维度级，每个变更内部用 ThreadPoolExecutor(6) 并行跑 6 个维度。第三层是 Claude 子进程级，用 Semaphore(4) 限制全局最多 4 个 Claude 进程同时运行。

为什么需要 Semaphore？因为理论上 2 个 review × 6 个维度 = 12 个 Claude 进程，但机器资源有限，4 个是实测的合理上限。

Git 方面，用 shallow clone（depth=10）做初始克隆，按需 fetch 单个变更的 ref。不拉全量历史，节省时间和磁盘。

## 第 9 页：架构优化 — 踩过的坑

> 【约 2 分钟】

做这个系统踩了不少坑，挑 4 个讲。

**坑 1：FETCH_HEAD 竞态**。多线程同时 git fetch，互相覆盖 FETCH_HEAD，导致 diff 显示的是别人的变更。解决方法是 fetch 到命名 ref——`refs/review/{change_id}/{revision}`，每个线程用独立的 ref，互不干扰。

**坑 2：共享工作区冲突**。多个 Claude 进程 cat 同一文件，可能读到错误版本。解决方法是给每个 change 创建独立的 git worktree，评审完就清理。

**坑 3：Skill 嵌入 prompt 膨胀**。13 个 Skill 全文嵌进 prompt，30KB 一个维度，上下文根本不够用。这就是刚才讲的 Skill 文件夹化的来源——被逼出来的优化。

**坑 4：executor.shutdown 永久阻塞**。Ctrl+C 之后 shutdown(wait=True) 挂死，进程退不掉。改成 wait=False 就好了。同时加了日志文件轮转，防止 claude_debug.log 无限膨胀。

这些坑的共同特点是：**它们都是传统工程问题，不是 AI 问题**。用信号量、命名 ref、文件隔离这些经典手段就能解决。

---

## 第 10 页：经验总结 + Q&A

> 【约 1.5 分钟，收尾】

总结下来，三条核心经验：

**第一，Agent 是调味料，不是主食。** 放在真正需要判断的地方——代码语义理解。确定性的事用确定性代码做，快、准、省。

**第二，Prompt 是成本。** 每个字都是钱，能省则省。Skill 文件夹化带来 99% 的缩减，而且效果反而更好。这个经验对所有用 LLM 做自动化的场景都适用。

**第三，并发是工程问题，不是 AI 问题。** AI 解决的是"理解"，不是"调度"。Semaphore、命名 ref、worktree 隔离，这些经典工程手段才是并发安全的关键。
